# Стандарти версіонування застосунку

Цей документ визначає **обов'язкові** правила управління версіями: автоматизація через Git Hooks та два підходи до зчитування версії.

---

## 🚫 ЖОРСТКІ ОБМЕЖЕННЯ (ANTI-PATTERNS)

| Рівень | Заборона | Правильна альтернатива |
|--------|----------|----------------------|
| **CRITICAL** | Хардкод версії в `.ts` / `.svelte` (`const VERSION = '1.0.42'`) | Build-time `import.meta.env.VITE_APP_VERSION` або runtime fetch |
| **HIGH** | Ручне редагування номера версії | Автоматичний Husky `pre-commit` хук |
| **HIGH** | Відсутність версії у копійованих логах | Заголовок звіту обов'язково містить `VERSION:` |

---

## 1. Автоматичне підняття версії (Bump Version)

### Контрольний список

- [ ] **Husky встановлено:** `husky` у `devDependencies`, ініціалізовано через `"prepare": "husky"`.
- [ ] **Pre-commit хук:** `.husky/pre-commit` викликає bump-скрипт:
```bash
#!/usr/bin/env sh
node scripts/bump-version.js
git add package.json static/app-version.json
```
- [ ] **Скрипт `scripts/bump-version.js`:**
  1. Читає `package.json`
  2. Інкрементує patch-версію (`1.0.41` → `1.0.42`)
  3. Записує нову версію у `package.json`
  4. Генерує `static/app-version.json`:
```json
{
  "version": "1.0.42",
  "buildTime": "2026-04-17T10:30:00.000Z"
}
```
- [ ] Розробнику **заборонено** вручну редагувати номер версії.

---

## 2. Зчитування версії

### Підхід A: Build-time injection (рекомендований)

Vite вбудовує версію на етапі збірки — **без мережевих запитів**, миттєво доступно.

#### Налаштування
- [ ] У `vite.config.ts` версія інжектується з `package.json`:
```typescript
import { defineConfig } from 'vite';
import { readFileSync } from 'fs';

const pkg = JSON.parse(readFileSync('./package.json', 'utf-8'));

export default defineConfig({
    define: {
        __APP_VERSION__: JSON.stringify(pkg.version),
    },
    // ... інша конфігурація
});
```

- [ ] У `src/app.d.ts` оголошено глобальний тип:
```typescript
declare const __APP_VERSION__: string;
```

- [ ] Використання у коді:
```typescript
const version = __APP_VERSION__; // '1.0.42' — вбудовано на етапі збірки
```

#### Переваги
- Нуль мережевих запитів
- Синхронний доступ (не потрібен `await`)
- Не залежить від HTTP-кешування

### Підхід B: Runtime fetch (для PWA / динамічного оновлення)

Корисний коли потрібно перевіряти оновлення **без перезбірки** (наприклад, PWA з тривалою сесією).

#### Налаштування
- [ ] **Cache Busting:** Параметр з версією або timestamp:
```typescript
async function getAppVersion(): Promise<string> {
    try {
        const res = await fetch(`${base}/app-version.json?v=${Date.now()}`);
        const data = await res.json();
        return data.version ?? 'unknown';
    } catch {
        return 'unknown';
    }
}
```
- [ ] **Базовий шлях:** Враховується `base` з `$app/paths` для проєктів у підпапці.

### Який підхід обрати?

| Критерій | Build-time (A) | Runtime (B) |
|----------|----------------|-------------|
| Для відображення в UI | ✅ Рекомендований | Працює |
| Для логів/звітів | ✅ Рекомендований | Працює |
| Для PWA "нова версія доступна" | ❌ Не підходить | ✅ Потрібний |
| Мережеві запити | Нуль | 1 fetch |
| Складність | Мінімальна | Потребує cache busting |

> **Рекомендація:** Використовуйте **Підхід A** для основного відображення версії. Додайте **Підхід B** тільки якщо маєте PWA з тривалими сесіями і потребуєте перевірки "нова версія доступна".

## 3. Відображення в UI

### Контрольний список

- [ ] **Видимість:** Версія виводиться мінімалістично — у футері, на сторінці налаштувань або в `+layout.svelte` (напр. `v1.0.42`).
- [ ] **Не хардкод:** Версія отримується через обраний підхід (A або B).
- [ ] **Формат:** Префікс `v` (напр. `v1.0.42`).

---

## 4. Версія у логах та звітах

### Контрольний список

- [ ] **Звіт LogCopyButton:** Заголовок **обов'язково** містить `VERSION:` (див. [DEBUGGING-v6.md](DEBUGGING-v6.md)).
- [ ] **LogService:** Зберігає версію як внутрішню властивість, встановлену при ініціалізації.
