# Svelte 5: Стан, Реактивність та Бізнес-логіка

Цей документ визначає **обов'язкові** правила роботи з реактивністю, архітектурою стану та побічними ефектами у Svelte 5 Runes. Усі пункти є критеріями прийняття (Acceptance Criteria).

---

## 🚫 ЖОРСТКІ ОБМЕЖЕННЯ (ANTI-PATTERNS)

| Рівень       | Заборона                                                 | Правильна альтернатива                                     |
| ------------ | -------------------------------------------------------- | ---------------------------------------------------------- |
| **CRITICAL** | `writable()`, `readable()`, `derived()` з `svelte/store` | `$state()`, `$derived()`, `$derived.by()`                  |
| **CRITICAL** | Оновлення `$state` всередині `$effect`                   | `$derived` / `$derived.by()` для залежних обчислень        |
| **CRITICAL** | Бізнес-логіка в `.svelte` файлах                         | Окремі `.svelte.ts` класи-контролери                       |
| **CRITICAL** | `createEventDispatcher()`                                | Колбек-пропси: `let { onchange } = $props()`               |
| **HIGH**     | Копіювання prop у локальний `$state`                     | Працювати напряму з пропсом або використовувати `$derived` |
| **HIGH**     | Глобальний мутабельний стан без класу                    | Класи з `$state` полями у `.svelte.ts` файлах              |

## 1. Управління Станом (State Management)

### 1.1 Single Source of Truth (SSoT)

- [ ] Кожна одиниця даних має **лише одне** джерело істини. Дублювання даних у різних `$state` змінних суворо заборонено.
- [ ] Усі обчислювані значення (фільтровані списки, підрахунки, форматовані рядки) реалізовані через `$derived` або `$derived.by()`, а **не** через ручне оновлення в `$effect`.

### 1.2 Глибока Реактивність (Deep Reactivity)

- [ ] Для складних об'єктів та масивів створюється окремий **клас** у файлі `.svelte.ts`, де поля визначені як `$state`.
- [ ] Масиви всередині класів мутуються через `push`, `splice`, присвоєння елемента за індексом — Svelte 5 Proxy робить це реактивним автоматично.

### 1.3 Інкапсуляція Мутацій

- [ ] Стан бажано змінювати через публічні методи класів-контролерів (напр. `counter.increment()`), що забезпечує єдину точку мутації та спрощує дебаг.
- [ ] Пряме присвоєння (`counter.count++`) допускається для простих випадків, де інкапсуляція не додає цінності.
- [ ] Кожен клас стану, що має початкове значення, **обов'язково** експонує метод `.reset()` для скидання у початковий стан (потрібно для тестів, logout-flow, повторного відкриття форми):

```typescript
class FormState {
	private static initial = { name: '', email: '' };
	name = $state(FormState.initial.name);
	email = $state(FormState.initial.email);

	reset() {
		this.name = FormState.initial.name;
		this.email = FormState.initial.email;
	}
}
```

> **Примітка:** На відміну від попередніх версій, пряме присвоєння полів `$state` є валідним у Svelte 5 і працює реактивно. Інкапсуляція — це архітектурна рекомендація, а не технічне обмеження.

### 1.4 URL як Стан

- [ ] Параметри фільтрів, пошуку, активного табу та пагінації зберігаються в URL (Search Params), а не в `let`-змінних.
- [ ] Для читання URL параметрів використовується `$page.url.searchParams`.
- [ ] Для зміни URL параметрів використовується `goto()` з `replaceState: true` або нативний `<a>` з правильними параметрами.

### 1.5 Синхронізація з localStorage

- [ ] Запис/зчитування з `localStorage` відбувається **виключно** через централізований `StorageService` (див. [STORAGE-NAMESPACE-v6.md](STORAGE-NAMESPACE-v6.md)).
- [ ] Синхронізація стану з `localStorage` реалізована через `$effect` **всередині** класу-контролера, а не у `.svelte` компонентах.

## 2. Побічні Ефекти (Side Effects)

### 2.1 Ізоляція `$effect`

- [ ] `$effect` використовується **тільки** для синхронізації з API браузера (`DOM`, `window`, `localStorage`, `matchMedia`) або інтеграції сторонніх Vanilla JS бібліотек.
- [ ] `$effect` **ніколи** не використовується для обчислення нового стану на основі іншого стану. Для цього є `$derived`.

### 2.2 Очищення (Cleanup)

- [ ] Будь-який `$effect`, що створює підписку, таймер (`setTimeout`, `setInterval`), `addEventListener`, `ResizeObserver`, `IntersectionObserver` або `MutationObserver` — **обов'язково** повертає функцію очищення:

```typescript
$effect(() => {
	const handler = () => {
		/* ... */
	};
	window.addEventListener('resize', handler);
	return () => window.removeEventListener('resize', handler);
});
```

### 2.3 Untrack

- [ ] Використовується `untrack()` для читання стану всередині `$effect` **без** створення реактивної залежності (коли потрібно прочитати значення, але не підписуватись на нього).

### 2.4 `$effect.root` — тільки для module-level ефектів

- [ ] `$effect.root()` використовується **виключно** для довготривалих ефектів поза життєвим циклом компонента (наприклад, у module-level singleton-класах).
- [ ] Якщо клас створюється **всередині** компонента (через `new` або `setContext`) — звичайний `$effect` достатній, `$effect.root` **не потрібен**.

```typescript
// ✅ Клас створюється в компоненті — звичайний $effect
class ThemeController {
	theme = $state<'light' | 'dark'>('light');

	constructor() {
		// Працює, бо конструктор викликається під час ініціалізації компонента
		$effect(() => {
			document.documentElement.setAttribute('data-theme', this.theme);
		});
	}
}

// ✅ Module-level singleton — потрібен $effect.root
const globalLogger = $effect.root(() => {
	const service = new LogService();
	$effect(() => {
		/* ... */
	});
	return () => {
		/* cleanup */
	};
});
```

### 2.5 `$inspect` для дебагу

- [ ] Для налагодження реактивних значень використовується `$inspect(value)` замість `console.log` всередині `$effect`.
- [ ] `$inspect` автоматично ігнорується в production збірці.

## 3. Архітектура Контролерів (Controller Pattern)

### 3.1 Розподіл відповідальності

- [ ] `.svelte` файли відповідають **лише** за: рендеринг UI, обробку DOM-подій, прив'язку до контролерів.
- [ ] `.svelte.ts` файли відповідають за: стан (`$state`), обчислення (`$derived`), бізнес-логіку, побічні ефекти (`$effect`).

### 3.2 Сервісний шар

- [ ] API-запити, Firebase, WebSocket, IndexedDB ізольовані у `.ts` файлах (не `.svelte.ts`), які не містять реактивності — це чисті async-функції.
- [ ] Контролер (`.svelte.ts`) **споживає** сервіс, а не реалізує мережеві виклики напряму.

### 3.3 Ін'єкція через Context API

- [ ] `setContext` / `getContext` використовуються для передачі глобальних сервісів (Settings, Auth, Theme) через дерево компонентів.
- [ ] Context **не** використовується як заміна пропсів для передачі даних між сусідніми компонентами.

### 3.4 Структура директорій

```
src/lib/
├── components/       # .svelte UI компоненти
│   ├── ui/           # базові: Button, Modal, Input
│   └── sections/     # складені секції сторінок
├── controllers/      # .svelte.ts класи з $state/$derived/$effect
├── services/         # .ts чисті async-сервіси (API, Firebase)
├── types/            # TypeScript інтерфейси та типи
├── utils/            # чисті функції-утиліти без побічних ефектів
└── config/           # статичні константи та конфігурації
```

### 3.5 Відсутність циклічних залежностей

- [ ] Відсутні циклічні імпорти між контролерами/сервісами. Залежності течуть в одному напрямку: `components → controllers → services → utils`.

### 3.6 Adapter Pattern для зовнішніх API

- [ ] Зовнішні API (Firebase, Stripe, REST-бекенд) обгортаються у власний адаптер у `services/`. Контролери залежать **лише** від цього адаптера, а не напряму від SDK:

```typescript
// services/userApi.ts — адаптер; зміна SDK не зачіпає контролерів
export const userApi = {
	async getById(id: string): Promise<User> {
		/* ... */
	},
	async update(id: string, patch: Partial<User>): Promise<void> {
		/* ... */
	}
};
```

- [ ] Контролер імпортує `userApi`, а не Firebase SDK напряму. Зміна провайдера = зміна одного файлу.
